# Plan

## Current behavior

`tools/generate_corpus.py` writes eight small PDFs directly from byte-oriented
helpers. Its page resources always point at object 3, a built-in Type 1
`/Helvetica` resource, and its content streams are ASCII text operators. The
generator creates `tests/fixtures/generated/*.pdf` but does not inspect font
resources or record source-font provenance.

`tests/fixtures/manifest.json` records classifications and some diagnostic and
browser expectations. The complete entries are structurally checked by
`tests/corpus_manifest.rs` and `tools/corpus.py`; the older `mixed-styles` and
`layout-breaks` entries are still incomplete. The validators currently have no
font integrity or font-processing expectation.

The diagnostic path is run by `tools/corpus.py` against the Rust binary with
PDFium. Browser behavior is checked separately by
`tools/browser_corpus.py`. The FontForge worker and generated `@font-face`
pipeline are covered by the adjacent font-processing work, so this change
supplies inputs and observable expectations rather than modifying that runtime.

## Intended behavior

The corpus generator produces the existing fixtures plus these deterministic
embedded-font fixtures:

- `embedded-vertical-slice.pdf`: two pages containing Liberation Sans text at two
  sizes, spaces and explicit spacing, rotated text, a PNG image, a vector
  rectangle, and an HTTPS link.
- `embedded-basic.pdf`: one page containing ordinary Liberation Sans text with an
  embedded TrueType program.
- `embedded-subset-name.pdf`: one page whose embedded Liberation Sans resource uses
  a six-letter subset-style PDF font name.
- `embedded-multiple-fonts.pdf`: one page using embedded Liberation Sans and
  Liberation Serif resources in separate text runs.
- `embedded-size-transform.pdf`: one page using the same Unicode characters at
  different sizes and with a rotation.

The manifest identifies each fixture's embedded-font source, required processed
font asset, processing requirement, and graphics background requirement in
addition to existing text, navigation, and screenshot expectations. The integrity test
parses the generated PDF object graph, follows font descriptors to FontFile2
streams, verifies TrueType signatures, and checks the declared font count and
names. It also regenerates the corpus and compares generated bytes.

Runtime checks use the existing diagnostic and browser commands. They report
native text, copied text, links, required assets, backgrounds, and screenshots.
Required processed-font assets make an unavailable or currently failing
converter visible rather than hidden by a fallback.

## Approach

Keep the existing generator responsible for corpus orchestration and move the
embedded-font PDF object construction into a focused native Python module,
`tools/embedded_font_pdf.py`. The module will build deterministic PDF objects,
font descriptors, FontFile2 streams, content streams, image resources, vector
paint, and link annotations. `tools/generate_corpus.py` will call that module
for the five named fixtures and retain the existing built-in-font fixtures.

Store the exact Liberation TTF inputs and license/provenance text in
`tests/fixtures/fonts/`. The generator embeds bytes from those files and never
downloads network content during corpus generation. A focused Python integrity
test will inspect the resulting PDFs and compare a second generation pass.

Add font fields to the existing JSON manifest rather than creating another
fixture registry. Extend `tests/corpus_manifest.rs`, `tools/corpus.py`, and
`tools/browser_corpus.py` only where they must validate or consume those
fields. Keep manifest entries for the pre-existing fixtures valid and do not
turn runtime expectations into claims that the converter already passes.

## Responsibilities and boundaries

- `tools/generate_corpus.py` owns corpus generation order and output location.
- `tools/embedded_font_pdf.py` owns deterministic embedded-font PDF assembly;
  it does not inspect converter output.
- `tests/fixtures/fonts/` owns committed font inputs and provenance records.
- `tests/embedded_font_fixtures.py` owns PDF byte integrity and deterministic
  generation tests.
- `tests/fixtures/manifest.json` owns fixture classifications and observable
  expectations, including font-specific fields.
- `tests/corpus_manifest.rs` owns Rust-side structural validation of all
  manifest entries.
- `tools/corpus.py` owns diagnostic page, text, link, and background expectations.
- `tools/browser_corpus.py` owns browser-visible native text, copied text,
  links, assets, and screenshot checks.
- `src/` remains unchanged; converter defects exposed by these fixtures belong
  to later implementation branches.

## Affected areas

- `tools/generate_corpus.py`
- `tools/embedded_font_pdf.py` (new)
- `tests/embedded_font_fixtures.py` (new)
- `tests/fixtures/fonts/LiberationSans-Regular.ttf`
- `tests/fixtures/fonts/LiberationSerif-Regular.ttf`
- `tests/fixtures/fonts/LICENSE-OFL.txt`

- `tests/fixtures/generated/embedded-*.pdf` (generated outputs)
- `tests/fixtures/manifest.json`
- `tests/corpus_manifest.rs`
- `tools/corpus.py`
- `tools/browser_corpus.py`
- `CONTEXT.md` for the repository's corpus commands and fixture documentation

## Decisions

- Use committed Liberation TTF inputs instead of network downloads so generation is
  reproducible offline and redistribution terms are reviewable.
- Use a focused PDF builder module because embedded font resources and image
  streams are a separate concern from the existing built-in-font fixtures.
- Keep the PDF builder intentionally limited to simple TrueType, ASCII fixture
  text, one image, one vector shape, and URI annotations; it is not a general
  PDF writer.
- Use explicit manifest fields for required source-font identities and
  processed assets so fixture integrity and runtime output are distinct checks.
- Mark processed font assets as required in the manifest and record actual
  runtime pass/fail results in completion notes; do not manufacture successful
  output or screenshot baselines.
- Leave the converter and existing fixture assertions unchanged except for
  manifest validation required to represent the new fixtures.

## Risks

- Incorrect PDF object references can make a fixture appear to contain a font
  while PDFium cannot load it; the integrity test must validate descriptor,
  FontFile2, and TrueType signature together.
- Font licensing or version metadata can become detached from committed bytes;
  provenance must name the exact files, version, source, license, and checksum.
- FontForge and browser availability differs by host; runtime status must remain
  explicit and separate from offline fixture-integrity success.
- Adding required manifest fields to only the new entries can leave older
  entries structurally inconsistent; validators must apply the existing rules
  to every fixture and font rules only to entries declaring embedded fonts.
- Embedding full TTF files increases fixture size; the chosen two Liberation inputs
  and five small PDFs are the accepted bounded corpus cost.

## Validation

- Run `python3 tools/generate_corpus.py` twice and verify the generated embedded
  PDF bytes are identical.
- Run `python3 -m unittest tests/embedded_font_fixtures.py` and verify each
  declared embedded fixture has the expected FontFile2 TrueType signature,
  declared font identity, and resource count.
- Run `cargo test --test corpus_manifest` and `python3 tools/corpus.py validate`
  to verify all manifest paths, expectations, classifications, and processing
  fields.
- Run `cargo fmt --check`, `cargo test`, `cargo clippy --all-targets
  --all-features -- -D warnings`, and `git diff --check`.
- When PDFium, FontForge, and the browser harness are configured, run the
  diagnostic and browser corpus commands and record each new fixture's actual
  pass/fail result, native text, generated font asset, background, link, and
  screenshot status in the completion notes.
- Review the final diff for absence of converter changes, arbitrary external
  PDFs, weakened existing assertions, and missing provenance.
